# xlyq-task-ops 公募基金营销任务管理平台设计

> 版本：v0.5（需求讨论稿）  
> 日期：2026-08-06  
> 状态：围绕“公募基金营销任务”继续确认

## 1. 项目定位

xlyq-task-ops 是一个手机端 Web 公募基金营销任务管理平台，用于让运营围绕基金产品、营销平台和合作机构创建、发布和管理营销任务，普通用户领取、执行并提交任务结果，机构查看本机构相关任务的流转和看板。

当前设计不再单独建立“需求”这一层。业务对象直接从“任务”开始，任务本身承载基金产品、机构关联、平台、执行要求、领取规则、提交材料、审核结果和流转记录。

### 1.1 业务语义

- 任务：指围绕公募基金产品或产品线发起的营销执行任务。
- 机构：指任务关联的销售/合作机构，首版只查看本机构相关任务。
- 平台：指营销任务投放或执行发生的平台、渠道或业务场景。
- 普通用户：指领取并执行营销任务的人，后续可按业务命名为营销人员、渠道人员或执行人。

第一版主线：

```text
运营创建营销任务
  -> 运营发布营销任务
  -> 普通用户领取任务
  -> 普通用户执行并提交营销结果
  -> 运营审核
  -> 任务完成 / 退回返工 / 重新流转
```

## 2. 首版目标

1. 支持运营创建公募基金营销任务，填写基金产品、关联机构、平台、截止时间、名额、提交规范等必填信息。
2. 支持运营发布任务、编辑任务、下架任务、审核提交结果和处理异常。
3. 支持普通用户在手机端浏览可领取任务、领取任务、提交任务和查看自己的任务看板。
4. 支持机构查看本机构相关营销任务的流转监控、完成情况和基础看板。
5. 保留任务状态历史、提交记录、审核记录和关键操作日志，保证流转可追溯。
6. 支持基础通知能力，包括领取成功、提交成功、审核通过、驳回返工、即将截止和超时提醒。

## 3. 首版不做

- 不单独建设“需求池”“需求承接”“需求拆解”模块。
- 不做复杂项目管理甘特图和资源排期。
- 不做完整低代码流程编排。
- 不做独立 IM 产品，任务内评论和审核反馈只覆盖任务协作必要范围。
- 不在 MVP 阶段拆成微服务，先采用模块化单体。

## 4. 用户角色

| 角色 | 主要职责 | 核心权限 |
| --- | --- | --- |
| 运营 | 创建营销任务、发布任务、任务管理、流转监控、审核结果、看板分析 | 查看全量或授权范围内任务，创建/发布/下架/审核/流转任务 |
| 机构 | 查看本机构营销任务进度、查看看板 | 查看本机构相关任务，查看流转、提交结果和统计 |
| 普通用户 | 领取营销任务、执行任务、提交结果、查看个人任务看板 | 浏览可领取任务，领取、提交、查看自己的任务 |

权限模型采用“角色权限 + 数据范围”：

- 运营：默认可看全部任务，后续可按区域、机构、任务类型限制范围。
- 机构：只能查看关联到自己机构的任务和对应统计，首版不提供创建和编辑能力。
- 普通用户：只能查看可领取任务、自己已领取任务和自己的提交记录。

## 5. 核心业务流程

### 5.1 运营创建营销任务

运营在手机端创建营销任务，至少填写：

- 任务标题
- 任务说明
- 任务类型
- 关联机构
- 平台
- 基金产品或产品线
- 营销活动主题
- 截止时间
- 领取名额
- 提交要求
- 审核规则说明
- 合规或物料要求
- 附件或示例材料（可选）

创建后进入“待发布”状态，由运营确认后发布，对普通用户开放领取。关联机构可在任务发布后查看任务流转和结果。平台字段用于标记营销任务投放或执行的业务场景，首版作为必填基础信息。

### 5.2 运营发布和管理任务

运营负责确认任务是否可发布，包括基金产品、机构关联、平台、内容完整性、提交要求、名额、截止时间和合规/物料要求。运营可执行：

- 发布任务
- 编辑任务
- 下架任务
- 查看领取情况
- 查看提交记录
- 审核通过
- 驳回返工
- 标记异常
- 关闭任务

### 5.3 普通用户领取和提交任务

普通用户在任务大厅查看可领取任务。领取后任务进入个人任务看板，用户按任务要求提交结果。

提交内容可以是：

- 文本说明
- 图片
- 文件
- 链接
- 表单字段

具体提交类型后续按任务类型配置。MVP 可以先支持文本、图片和链接。

### 5.4 审核与返工

普通用户提交后，领取记录进入“待审核”。运营审核结果：

- 通过：领取记录完成，计入任务完成量。
- 驳回：填写驳回原因，用户进入返工状态，可重新提交。
- 作废：适用于无效提交、违规提交或用户放弃等场景。

任务整体是否完成，取决于任务名额、完成量和运营关闭规则。

## 6. 状态模型

任务状态描述“任务是否对外开放以及整体执行进度”：

```text
草稿 -> 待发布 -> 可领取 -> 进行中 -> 已完成
                         |        |
                         |        +-> 已下架
                         +-> 已下架

可领取 / 进行中 -> 已过期
```

领取记录状态描述“某个普通用户领取后的执行进度”：

```text
已领取 -> 待提交 -> 待审核 -> 已通过
                     |
                     +-> 返工中 -> 待审核
                     |
                     +-> 已作废

已领取 / 待提交 / 返工中 -> 已放弃
```

### 6.1 任务状态说明

- `草稿`：运营创建后暂存，未提交发布。
- `待发布`：运营已创建完成，等待确认发布。
- `可领取`：已发布，对符合条件的普通用户开放领取。
- `进行中`：已有用户领取或已有提交记录。
- `已完成`：任务达到完成条件并关闭。
- `已下架`：运营主动下架，普通用户不可再领取。
- `已过期`：超过截止时间后仍未完成或未关闭。

### 6.2 领取记录状态说明

- `已领取`：用户领取成功。
- `待提交`：用户需要提交任务结果。
- `待审核`：用户已提交，等待运营审核。
- `返工中`：提交被驳回，用户需要补充或重做。
- `已通过`：审核通过。
- `已作废`：提交被判定无效。
- `已放弃`：用户主动放弃或超时释放名额。

每次状态变化都写入状态历史，记录操作人、前后状态、原因、时间和来源端。

## 7. 手机端页面规划

### 7.1 运营端

- 首页看板：待发布、可领取、进行中、待审核、异常、已完成。
- 任务管理：任务列表、筛选、搜索、发布、下架、编辑。
- 任务详情：任务要求、领取人、提交记录、评论、操作时间线。
- 审核台：集中处理待审核提交，支持通过、驳回、作废。
- 流转监控：按机构、状态、任务类型、截止时间查看流转。
- 数据看板：发布数、领取数、提交数、通过率、超时率、完成率。

### 7.2 机构端

- 首页看板：本机构任务总览、进行中、待发布、已完成、异常。
- 任务列表：查看关联到本机构的任务列表。
- 任务详情：查看领取进度、提交结果、流转记录。
- 数据看板：按时间和任务类型查看完成情况。

### 7.3 普通用户端

- 任务大厅：查看可领取任务，按类型、奖励、截止时间筛选。
- 任务详情：查看任务说明、提交要求、名额和截止时间。
- 我的任务：待提交、待审核、返工中、已完成。
- 提交任务：上传材料、填写说明、提交链接。
- 消息中心：领取成功、审核结果、返工原因、截止提醒。

三角色首页的详细设计见 [公募基金营销任务三角色首页设计](HOMEPAGE_DESIGN.md)。

## 8. 任务交互能力

为了打通与领取者的交互，第一版需要围绕任务提供轻量沟通能力：

- 任务公告：运营对所有领取者补充说明。
- 任务评论：用户就自己领取的任务发起问题或补充说明。
- 审核反馈：驳回时必须填写原因。
- 重新提交：返工后保留历史提交记录。
- 催办提醒：运营可对未提交用户发送提醒。
- 系统通知：状态变化和截止时间触发通知。

评论和通知只服务于任务协作，不作为独立聊天系统。

## 9. 功能模块

### 9.1 任务中心

## 10. 推荐技术架构

首版采用模块化单体：

```text
Mobile Web
   |
API / BFF
   |
+-----------+-------------+--------------+---------------+
| 任务模块  | 审核模块    | 通知模块     | 看板模块      |
+-----------+-------------+--------------+---------------+
| 机构用户  | 权限模块    | 审计日志     | 文件模块      |
+-----------+-------------+--------------+---------------+
   |
MySQL + Redis + 对象存储
   |
异步任务：通知、超时扫描、统计聚合、Webhook 重试
```

建议技术栈：

- 前端：React + TypeScript + Vite，按手机端 Web 优先设计。
- 后端：TypeScript + NestJS 或同等模块化 Web 框架。
- 数据库：MySQL。
- 缓存和异步队列：Redis。
- 文件：S3 兼容对象存储。
- 部署：Docker。

如果团队已有固定 Java、Go、Python 或前端组件体系，应优先复用已有标准。

## 11. 后端模块边界

```text
src/
  modules/
    tasks/          # 任务、领取记录、状态机、提交记录
    reviews/        # 审核动作、驳回原因、审核记录
    organizations/  # 机构、机构成员、机构数据范围
    users/          # 普通用户、运营用户、角色
    notifications/  # 通知模板、通知投递、提醒规则
    analytics/      # 看板指标和统计查询
    files/          # 附件元数据和上传下载
    audit/          # 操作日志和状态历史
  shared/
    database/
    auth/
    errors/
    pagination/
```

任务状态迁移必须由后端领域服务校验，前端只展示当前用户可执行的动作。

## 15. 待确认事项

1. 机构是否只能查看任务进度，还是也能查看用户提交的原始材料？
2. 平台字段首版是否只做单选，还是需要同时支持多平台投放？
3. 基金产品字段首版是否关联标准产品库，还是先使用手工录入？
4. 任务是否有奖励、积分、佣金或结算机制？
5. 普通用户领取任务前是否需要资格校验，例如实名认证、等级、标签、地域、机构绑定？
6. 一个任务是单人领取，还是多人按名额领取？
7. 审核只由运营完成，还是机构后续也可能参与终审？
8. 提交材料首版必须支持哪些类型：文本、图片、文件、视频、链接、表单？
9. 超时后任务名额是否自动释放？
10. 普通用户是否允许主动放弃任务？放弃后是否有限制或惩罚？

在这些问题未确认前，默认按以下规则推进：运营创建、发布和审核公募基金营销任务；任务必须关联机构、平台和基金产品；机构只查看本机构任务流转、看板和审核后的结果；普通用户按名额领取；首版支持文本、图片和链接提交；任务使用自然时间截止；普通用户可以放弃，放弃释放名额。
